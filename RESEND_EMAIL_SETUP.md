# Resend Email Setup — Donation Receipt Delivery

This guide documents how to wire up [Resend](https://resend.com) to automatically email the
donation-receipt PDF (already generated by `api/receipts/generate.ts`) to the donor's email
address (already collected on the donation form and threaded through to
`api/payments/verify-payment.ts` as `donorEmail`).

This is a **documentation-only** guide — none of the steps below have been applied to the
codebase yet. Follow it top to bottom to implement the feature.

## Why Resend

- Razorpay's native 80G/receipt-email feature is tied to its **Payment Button** product and is
  configured entirely in the Razorpay dashboard. This project uses the custom Orders/Subscriptions
  API + webhook flow, which Razorpay's native feature doesn't support — so a custom send step is
  needed regardless of provider.
- No new infrastructure is required beyond Vercel. Resend is just an HTTPS API call from inside
  the existing serverless function — same shape as the Razorpay and Google Sheets calls already
  in `api/`.
- Resend is SOC 2 Type II certified, encrypts data at rest (AES-256) and in transit (TLS 1.3+),
  and has a generous free tier (3,000 emails/month, 1 verified domain) that comfortably covers a
  donation site's volume.
- Caveat worth knowing: Resend stores data in the US (relevant under India's DPDP Act) and is
  **not** HIPAA or ISO 27001 certified. Email transport is never end-to-end encrypted no matter
  which provider is used — see the **Security considerations** section below for how to mitigate
  that at the PDF level instead of the transport level.

## Prerequisites

1. A [Resend](https://resend.com) account.
2. A verified sending domain (Settings → Domains → Add Domain → add the DNS records Resend gives
   you — SPF/DKIM TXT records — at your DNS provider; verification is usually near-instant to a
   few hours). Until a domain is verified, Resend only lets you send from
   `onboarding@resend.dev`, which is fine for testing but should not be used in production.
3. An API key (Settings → API Keys → Create API Key). Scope it to **Sending access** only — it
   doesn't need read access to anything else.

## 1. Install the dependency

```bash
npm install resend
```

This is a net-new dependency — the project currently has no email-sending package
(`pdf-lib`, `googleapis`, and `razorpay` are the only service-integration deps today).

## 2. Add environment variables

Append a new section to `.env.example`, following the same style as the existing `# Razorpay`
and `# Google Sheets` sections:

```diff
 # Google Sheets (api/forms/submit.ts) - see GOOGLE_SHEETS_SETUP.md
 GOOGLE_SERVICE_ACCOUNT_EMAIL=
 GOOGLE_SERVICE_ACCOUNT_PRIVATE_KEY=
 GOOGLE_SHEETS_SPREADSHEET_ID=
+
+# Resend (api/_lib/email.ts) - see RESEND_EMAIL_SETUP.md
+RESEND_API_KEY=
+RESEND_FROM_EMAIL=
```

- `RESEND_API_KEY` — the key created above.
- `RESEND_FROM_EMAIL` — must be `name@your-verified-domain.com`. Something like
  `receipts@isaahasi.org` or `donations@isaahasi.org` reads well to a donor.

Then set the real values in Vercel: **Project → Settings → Environment Variables** (and in your
local `.env` for `vercel dev` testing — this project doesn't commit a real `.env`, only
`.env.example`).

## 3. Create `api/_lib/email.ts`

This mirrors the existing `api/_lib/sheets.ts` pattern: a small module that owns one external
client, reads its own env vars at module scope, exports one focused async function, and throws
on failure so the caller decides how to handle it.

```typescript
/**
 * Resend email helper.
 *
 * Sends the donation-receipt PDF to the donor by email via Resend's HTTPS
 * API. See RESEND_EMAIL_SETUP.md for how to provision the API key, verify
 * a sending domain, and set the env vars below.
 */

import { Resend } from "resend";

const RESEND_API_KEY = process.env.RESEND_API_KEY!;
const FROM_EMAIL = process.env.RESEND_FROM_EMAIL!;

const resend = new Resend(RESEND_API_KEY);

export interface ReceiptEmailInput {
  to: string;
  donorName: string;
  receiptNo: string;
  amount: number;
  pdfBytes: Uint8Array;
}

/**
 * Emails the receipt PDF to the donor. Throws on failure — the caller is
 * responsible for catching and deciding whether that should fail the
 * response (it shouldn't; see api/payments/verify-payment.ts).
 */
export async function sendReceiptEmail(input: ReceiptEmailInput): Promise<void> {
  const { error } = await resend.emails.send({
    from: `iSaahasi Academy India Foundation <${FROM_EMAIL}>`,
    to: input.to,
    subject: `Your donation receipt — ${input.receiptNo}`,
    html: `
      <p>Dear ${input.donorName},</p>
      <p>Thank you for your generous donation of ₹${input.amount.toLocaleString("en-IN")}
      to iSaahasi Academy India Foundation.</p>
      <p>Your official donation receipt is attached to this email. Please keep it for your
      records — it may be required for tax purposes.</p>
      <p>With gratitude,<br/>iSaahasi Academy India Foundation</p>
    `,
    attachments: [
      {
        filename: `receipt-${input.receiptNo}.pdf`,
        content: Buffer.from(input.pdfBytes),
      },
    ],
  });

  if (error) {
    throw new Error(`Resend send failed: ${error.message}`);
  }
}
```

Notes specific to this codebase:

- `Buffer.from(input.pdfBytes)` — Resend's Node SDK wants a `Buffer` (or base64 string) for
  `attachments[].content`; `generateReceiptPdf` returns a `Uint8Array`, so this conversion is
  required.
- Vercel functions in this project run on the Node runtime (not Edge) because `api/_lib/receipt.ts`
  already uses `fs/promises` to read the template PDF — `resend` is a plain Node/HTTPS client and
  is compatible with that same runtime, so no runtime-config changes are needed.

## 4. Expose the PDF bytes from `buildAndSaveReceipt`

Right now `buildAndSaveReceipt` in `api/receipts/generate.ts` generates `pdfBytes` in memory,
writes them to disk, and returns only `{ receiptNo, path }` — the bytes themselves are discarded
after the write. The email step needs those same bytes directly, without re-reading them from
disk (disk writes under `generated/` are not reliable in a serverless environment: each
invocation gets its own ephemeral filesystem, so a file written in one request is not guaranteed
to be readable by a later one).

Add `pdfBytes` to the returned result:

```diff
 export interface ReceiptGenerationResult {
   receiptNo: string;
   path: string;
+  pdfBytes: Uint8Array;
 }
```

```diff
   const pdfBytes = await generateReceiptPdf(data);

   await mkdir(GENERATED_DIR, { recursive: true });
   const fileName = `receipt-${input.paymentId || Date.now()}.pdf`;
   const absolutePath = path.join(GENERATED_DIR, fileName);
   await writeFile(absolutePath, pdfBytes);

-  return { receiptNo, path: path.join('generated', fileName) };
+  return { receiptNo, path: path.join('generated', fileName), pdfBytes };
 }
```

The local disk write can stay as-is for local/dev convenience — it's just no longer the only way
the caller gets at the bytes.

## 5. Wire the send into `api/payments/verify-payment.ts`

`donorEmail` is already present on `VerifyPaymentBody` and already flows in from
`paymentService.ts`'s `verifyOnce` — it just isn't used yet. Add the email send as a second
best-effort step, right after the existing receipt-generation try/catch, following the exact
same "never fail the response" pattern already used there:

```diff
 import { validatePaymentVerification } from 'razorpay/dist/utils/razorpay-utils.js';
 import { buildAndSaveReceipt } from '../receipts/generate';
+import { sendReceiptEmail } from '../_lib/email';
```

```diff
   let receiptPath: string | null = null;
+  let receiptNo: string | null = null;
+  let pdfBytes: Uint8Array | null = null;
   try {
     const result = await buildAndSaveReceipt({
       donorName: body.donorName ?? 'Donor',
       amount: typeof body.amount === 'number' && Number.isFinite(body.amount) ? body.amount : 0,
       purpose: body.purpose ?? 'Donation',
       paymentId: razorpay_payment_id,
       paymentMethod: body.paymentMethod ?? 'Online (Razorpay)',
     });
     receiptPath = result.path;
+    receiptNo = result.receiptNo;
+    pdfBytes = result.pdfBytes;
   } catch (err) {
     console.error('verify-payment: receipt generation failed', razorpay_payment_id, err);
   }

+  // Best-effort email delivery. Only attempted if the PDF above succeeded
+  // and a donor email was supplied — a missing/failed send must never fail
+  // this response, since the payment itself is already verified and real.
+  if (pdfBytes && body.donorEmail) {
+    try {
+      await sendReceiptEmail({
+        to: body.donorEmail,
+        donorName: body.donorName ?? 'Donor',
+        receiptNo: receiptNo!,
+        amount: typeof body.amount === 'number' && Number.isFinite(body.amount) ? body.amount : 0,
+        pdfBytes,
+      });
+    } catch (err) {
+      console.error('verify-payment: receipt email failed', razorpay_payment_id, err);
+    }
+  }
+
   return Response.json({ verified: true, paymentId: razorpay_payment_id, receiptPath });
```

No change is needed on the frontend (`paymentService.ts`) — `donorEmail` is already sent in the
`verifyOnce` request body.

## 6. Security considerations

The earlier discussion in this project flagged that these are financial/tax documents and asked
whether Resend is safe to use for them. Two separate layers matter here:

- **Transport/storage (Resend's side):** SOC 2 Type II certified, AES-256 at rest, TLS 1.3+ in
  transit — reasonable for this use case, but data is stored in the US and retained ~30 days on
  Resend's side, and it's not HIPAA/ISO 27001 certified. This is the same tradeoff any
  third-party transactional-email provider (Gmail SMTP, SendGrid, Postmark, SES) carries — none
  of them are end-to-end encrypted once a message is composed into an email body/attachment.
- **The PDF content itself:** the real mitigation is making the attachment unreadable without a
  password, independent of how it's transported. **Important caveat:** `pdf-lib` (already used
  for generation) does **not** support PDF encryption/password-protection — there's no API for it
  in that library. To add password protection you'd need to either:
  - Pipe the generated bytes through a separate encryption step (e.g. a WASM build of `qpdf`, or
    an unmaintained `pdf-lib` fork that adds encryption — none of these are currently a
    dependency, so this is new surface area to vet before adding), or
  - Switch the PDF generation itself to a library with native encryption support (e.g. `pdfkit`
    has `encrypt` options), which would mean reimplementing the existing hand-tuned coordinate
    overlay logic in `api/_lib/receipt.ts` — a nontrivial rewrite, not a drop-in.

  Given that cost, treat password-protection as a **separate follow-up decision**, not part of
  this email-sending step. If it's not added, the practical mitigation is: don't put the donor's
  full PAN number on the receipt PDF (only mask/partial it, if it appears at all), since the PAN
  + name combination is the sensitive pairing, not the donation amount itself.

## 7. Testing locally

```bash
npx tsx -e "
import { sendReceiptEmail } from './api/_lib/email';
import { generateReceiptPdf } from './api/_lib/receipt';

const pdfBytes = await generateReceiptPdf({
  receiptNo: 'TEST-001',
  date: '13/10/2026',
  receivedFrom: 'Test Donor',
  amountInWords: 'Rupees Five Hundred Only',
  amountNumber: '500',
  paymentMethod: 'Online (Razorpay)',
  purpose: 'Donation',
});

await sendReceiptEmail({
  to: 'your-own-email@example.com',
  donorName: 'Test Donor',
  receiptNo: 'TEST-001',
  amount: 500,
  pdfBytes,
});

console.log('sent');
"
```

Requires `RESEND_API_KEY` and `RESEND_FROM_EMAIL` to be set in your shell/`.env` first. Check the
Resend dashboard's **Logs** tab to confirm delivery and inspect the rendered email + attachment.
